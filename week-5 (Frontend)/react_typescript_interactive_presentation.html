02 · The problem

When UI updates become manual work

Vanilla JavaScript · familiar from Week 2
let count = 0;

button.addEventListener("click", () => {
  count++;
  output.textContent = String(count);
});

We store the value, find the right element, then update the DOM ourselves.

What gets harder at scale?

More moving parts

Many UI elements may depend on the same data.

More coordination

Manual DOM updates can become spread across many handlers.

More chances to drift

The displayed interface can get out of sync with the app's data.

Direct DOM manipulation is still useful. React is valuable when we want a consistent, component-based way to describe a changing UI.
Week 2 → Week 5 · Bridge example

You already built the behavior. React changes the workflow.

Your Week 2 sample recreates a tiny piece of React: state values, setter functions, and a full UI refresh.

Week 2 · Vanilla JavaScript + DOM
let hooks = [];
let hookIndex = 0;

const useState = (initialValue) => {
  const index = hookIndex;
  if (hooks[index] === undefined) {
    hooks[index] = initialValue;
  }

  const setState = (next) => {
    const value = typeof next === "function"
      ? next(hooks[index])
      : next;

    if (hooks[index] !== value) {
      hooks[index] = value;
      refreshUI();
    }
  };

  hookIndex++;
  return [hooks[index], setState];
};

Your mini implementation stores hook values by call order, then clears and rebuilds the DOM when state changes.

React · JSX + built-in hook
import { useState } from "react";

function App() {
  const [nPress, setNPress] = useState(0);
  const [title, setTitle] = useState("Hello World");

  return (
    <main className="container">
      <h3>{title}</h3>
      <p>Button pressed {nPress} times</p>

      <button onClick={() =>
        setNPress(prev => prev + 1)
      }>
        Press me
      </button>

      <button onClick={() =>
        setTitle("Another Title")
      }>
        Change title
      </button>
    </main>
  );
}

React manages hook state, rendering, and DOM updates. You describe the UI instead of manually creating each element.

Teaching point: This is an educational miniature—not a replacement for React. A real implementation needs more than a global array and a full DOM rebuild. React also has rules for hook order, component identity, rendering, and scheduling.

What your code teaches

  • hooks[] stores state values.
  • hookIndex identifies each hook call by its order during a render.
  • setNPress(prev => prev + 1) updates from the previous value.
  • refreshUI() removes and rebuilds the DOM.

In React, use the real useState hook. Don't implement your own hook system in application code.

Ask the class: “Which lines in the React version replace document.createElement, appendChild, and removeElements?” Look for the JSX return and React's render cycle.
Code reading · Important caveat

What the mini useState gets right—and what it skips.

Good learning model

  • State survives a refresh.
  • Setter can accept a value or updater function.
  • Updating state triggers a rerender.
  • Hook calls rely on a stable call order.

Not production React

  • One global hook array cannot isolate multiple components.
  • It rebuilds all DOM nodes on every update.
  • It doesn't handle component identity, effects, batching, or scheduling.
  • It doesn't enforce the Rules of Hooks.
Use this sample to explain the idea behind state and rerendering—not to suggest that React itself is implemented with only these few lines.

06 · JSX / TSX

HTML-like syntax, with JavaScript expressions.

const name = "Ethan";

function App() {
  return (
    <section>
      <h1>Hello, {name}!</h1>
      <p>Welcome to React.</p>
    </section>
  );
}

Remember these rules

  • JSX describes the interface inside JavaScript.
  • Curly braces insert JavaScript expressions.
  • Use className, not class.
  • Return one parent element or a fragment.
  • TSX is JSX with TypeScript type-checking support.
Connect to Week 1: the markup and CSS concepts are familiar. React changes how the UI is assembled and updated.
07 · Props

Props are inputs to a component.

interface GreetingProps {
  name: string;
}

function Greeting({ name }: GreetingProps) {
  return <h2>Hello, {name}!</h2>;
}

// Use the same component with different data:
<Greeting name="Ethan" />
<Greeting name="Derick" />

Try changing the prop

Hello, Ethan!

Conceptually: <Greeting name="..." />

Props are read-only from the receiving component's perspective. They configure a component; they are not its private changing state.
08 · TypeScript

Catch type mistakes before runtime.

function add(a: number, b: number): number {
  return a + b;
}

add(2, 3);      // Valid
add("2", 3);    // Type error

TypeScript checks the code during development/build; it does not automatically validate external data at runtime.

Useful starter types

string · text

number · numeric values

boolean · true / false

Task[] · array of Task objects

"open" | "done" · a limited set of allowed values

TypeScript is not a different runtime from JavaScript. It adds static analysis and its types are erased when the code is emitted as JavaScript.
09 · Typed components

Make component contracts clear.

interface UserCardProps {
  name: string;
  yearLevel: number;
  isActive: boolean;
}

function UserCard({ name, yearLevel, isActive }: UserCardProps) {
  return (
    <article className="user-card">
      <h2>{name}</h2>
      <p>Year level: {yearLevel}</p>
      <p>{isActive ? "Active" : "Inactive"}</p>
    </article>
  );
}

Required props

TypeScript can flag a missing name or an incorrect type.

Optional props

Use subtitle?: string when a value may be omitted.

11 · Props vs state

Two different jobs.

📦

Props

Data passed into a component.

Example: a profile card receives a person's name.

Input
🔄

State

Data that can change over time and affect what is rendered.

Example: whether a menu is open.

Changing data
A component should not mutate its props. State updates should use React's setter function, not direct mutation.
12 · useState

Let the interface respond to state.

const [count, setCount] = useState<number>(0);

<button onClick={() => setCount(count + 1)}>
  Increment
</button>

React renders the count from state. The state setter requests an update.

A regular variable changing does not, by itself, tell React to render again.

14 · Lists + conditions

Render UI from data.

tasks.map((task) => (
  <li key={task.id}>
    {task.completed ? "✓" : "○"}
    {task.title}
  </li>
))

JavaScript's map() renders one UI item per data item. Conditional expressions choose what to show.

Why the key?

React uses stable keys to match list items across updates.

Prefer a stable ID when available. Array indexes can be problematic if items are reordered, inserted, or deleted.

Think of the UI as a projection of your data: change the data correctly, and React can update the visible list.

17 · Connect to PHP / Laravel

Frontend and backend have different responsibilities.

React + TypeScript

UI, forms, state, feedback

↕ HTTP request / response · JSON
PHP / Laravel API

Validation, business rules, authentication, authorization

↕
Database

Persistent records

Frontend validation helps users. It is not a security boundary: the backend must validate and authorize every relevant request.
const response = await fetch("/api/tasks");
if (!response.ok) throw new Error("Failed to load tasks");
const data = await response.json();

TypeScript types do not validate JSON at runtime. Check untrusted API data and handle loading, error, and empty states.

18 · Avoid the traps

Common beginner mistakes

❌ Mutating state directly

Use new arrays/objects with patterns like map, filter, and spread.

❌ Confusing props and state

Props are inputs; state represents changing data owned by a component or state owner.

❌ Calling handlers during render

Pass a function: onClick={handleClick}.

❌ Ignoring keys and types

Use stable list keys and meaningful types instead of reaching for any.

❌ One giant component

Split the UI into focused pieces with clear responsibilities.

❌ Trusting frontend validation

Backend validation and authorization are still required.
