Connect securely; grant only needed access

Understand permissions

DEPLOYMENT PIPELINE10
10 · Configuration

What belongs in .env?

Configuration changes between environments. Application code should not need to change just because the database host or app URL changes.

.env example — placeholders only
APP_NAME="Notes App"
APP_ENV=production
APP_DEBUG=false
APP_URL=https://notes.example.com

DB_CONNECTION=sqlite
DB_DATABASE=/var/www/notes-app/database/database.sqlite

Good candidates

Environment mode, URL, database connection details, mail settings, third-party API credentials.

Never commit secrets

Keep .env out of Git. Commit .env.example with safe placeholders instead.

CONFIGURATION11
11 · Security

Production configuration is a security boundary

Do

  • Set APP_ENV=production.
  • Set APP_DEBUG=false.
  • Protect .env and private keys.
  • Use least-privilege file permissions.
  • Use HTTPS for real public deployments.

Don't

  • Commit .env to Git.
  • Paste credentials into screenshots or chat.
  • Expose Laravel's project root as the web root.
  • Assume a hidden filename is secure.
  • Enable verbose errors for public visitors.
If a secret is accidentally published, removing it from the latest commit is not enough. Revoke or rotate the exposed credential.

12 · Prepare the application

Before touching the server

  1. Confirm the app works locally
    Create a note, list notes, refresh, confirm data persists.
  2. Commit the dependency lockfile
    composer.lock makes dependency installation reproducible.
  3. Keep configuration out of Git
    Commit .env.example; ignore the real .env.
  4. Know the runtime requirements
    Check the Laravel version's required PHP version and extensions.

php artisan --version
composer validate
git status

LIVE DEMO · PREPARE16
16 · Live demo / Step 3

Configure, migrate, and optimize

example for a SQLite demo
touch database/database.sqlite
# Set the DB_DATABASE path in the production .env
# Set ownership/permissions for this file and storage directories
php artisan config:clear
php artisan migrate --force
php artisan config:cache
php artisan route:cache

Why --force?

Production migrations require explicit confirmation to reduce accidental changes.

Why cache config?

Laravel can load configuration more efficiently; refresh the cache after configuration changes.

Back up production data before schema changes. Never point a demo migration at an unknown or real production database.
LIVE DEMO · CONFIGURE17
17 · Live demo / Step 4

Point Nginx at Laravel's public/ directory

Nginx server-block concept — adapt before use
server {
    listen 80;
    server_name notes.example.com;
    root /var/www/notes-app/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    }

    location ~ /\.(?!well-known).* {
        deny all;
    }
}
The PHP-FPM socket and configuration paths vary by server. Test the configuration before reloading: sudo nginx -t.

20 · Before calling it done

Production readiness checklist

Application

  • Dependencies installed from lockfile
  • Environment configured
  • Migrations reviewed and applied
  • Storage/cache permissions correct

Server

  • Only required ports exposed
  • Services running and config validated
  • Web root points to public/
  • HTTPS and DNS checked where applicable

Security

  • APP_DEBUG=false
  • No secrets in Git
  • Least-privilege access
  • Updates and credentials managed

Operations

  • Logs can be inspected
  • Database backup/restore plan
  • Health check works
  • Rollback plan documented
